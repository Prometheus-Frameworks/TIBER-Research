All runs used the reviewed/frozen `tiber-agent-entry/v0` protocol from PR #11 (`b004d9813f905e734e18d9c98ebd363a31b71aab`). Synthetic-test status was withheld from the agents.

It also disclosed that it was emitting five objects in one reply despite v0's one-object-per-message rule, and used `00:00:00Z` placeholder timestamps rather than a truthful observed clock.

### Architectural finding: the tree is the map, not the mission

The operator's actual job is not to construct causal trees. The operator describes what they manage/care about and why. The agent UAVs the relevant terrain. TIBER preserves the resulting map.

Working formulation:

> **Shared Reality + operator context + management horizon → context-bound entity model.**

Examples:

- A redraft Jaylen Warren model cares about receiving role, current competition, health, and whether the RB2/flex mechanism remains intact this season; it does not need a three-year career projection.
- The same Justin Jefferson can require different monitoring in different leagues depending on how much team value is concentrated in him, roster age, and management horizon.
- A Jets fan/researcher could maintain team/unit models for producing strong public research without playing fantasy at all.
- A scout could use the same substrate around privately supplied prospect files; the agent helps allocate attention and expose gaps without converting private material into Shared Reality.

### UX finding: governance belongs behind the conversational surface

The strongest failure mode was not weak governance; it was **governance leakage**. Opus showed that a capable model can obey the protocol so literally that the human is forced to adjudicate ontology (`required` vs `contributing`, one claim vs two, stance, falsifier semantics) instead of talking naturally about football.

New principle:

> **Governance should constrain the agent's cognition and durable artifacts without unnecessarily colonizing the human conversation.**

The agent should own translation from natural language into nodes/edges/provenance/epistemic classes. Clarification is justified only when ambiguity materially changes the map or subject identity and cannot be resolved from available reality.

A useful distinction can remain inside TIBER without requiring an operator question. Example: `Achane is a fade at cost and does not finish as an RB1` can internally retain two separable claims without asking the user to perform schema design unless the distinction becomes decision-relevant.

### Artifact-handoff finding

Operator confirmation should **not** mean "show me the serialization."

Ideal flow:

```text
natural conversation
  → agent maps terrain
  → operator confirms/corrects interpretation
  → agent persists context-bound entity model to operator workspace
  → chat may disappear
  → another agent later retrieves the same model
  → current Shared Reality is compared against the preserved model
  → observations/challenges append; original state is never rewritten
```

Human-facing completion should look more like:

> “Got it. I saved all five to [personal workspace].”

not thousands of lines of JSON.

This is analogous to the existing GitHub workflow: the operator approves an issue/write; the agent invokes the durable system and reports the result rather than exposing the API payload.

### Memory / portability finding

Do **not** make agent conversational memory the authoritative store for these models. TIBER should persist the governed object. A future ChatGPT/Claude/Grok/etc. can retrieve `[personal workspace] → [player]` and understand why the asset mattered even if it never saw the originating conversation.

This supports the broader architecture direction: the user's TIBER account/workspace is persistent football world state; the user's preferred agent is a lens/operator interface over it.

### Next missing primitive: small agent persistence/retrieval surface

Before building a large share viewer or broad MCP surface, specify the smallest lifecycle that proves portability:

1. resolve an entity to canonical TIBER identity;
2. save a confirmed context-bound entity model to an operator workspace;
3. retrieve that model in a fresh agent session;
4. append a new observation/challenge without rewriting the original model.

Candidate initial tool vocabulary (names provisional):

- `resolve_entity`
- `save_entity_model`
- `get_entity_model`
- `append_entity_observation`

An MCP server is a plausible transport for this capability, but the contract/lifecycle should be specified from the [personal workspace] trace before choosing or expanding transport architecture. Do not expose all eleven repositories as the product API.

### Follow-up protocol corrections suggested by User Zero

For a future v0.1 (do not mutate the frozen v0 pilot artifact):

- explicitly state that schema/provenance/epistemic bookkeeping is agent-facing and should remain invisible unless requested;
- operator confirmation authorizes preservation of the interpreted model; it does **not** request JSON serialization;
- never emit the machine representation unless explicitly requested or required by an attached persistence tool;
- clarify how an agent should persist multiple confirmed proposals when the conversational interface cannot produce multiple messages atomically;
- timestamps must be truthful observations; never manufacture a valid-looking placeholder timestamp and explain it afterward;
- distinguish capability modes: governance is always present, while Shared Reality/private context/external research/persistence capabilities vary by container.

### Revised interpretation of #10

The original issue remains useful, but the self-pilot suggests the terminal product is broader than "Let’s Cook list → tree viewer." A shareable tree can remain a view over the durable model, and Jeremiyah Love remains an excellent prospective golden trace. The more fundamental primitive is:

Next implementation work should begin from this finding rather than optimizing the current intake ceremony.
