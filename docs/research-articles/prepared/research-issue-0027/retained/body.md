## Objective

Audit whether TIBER should develop a continuously updated, time-aware estimate of an NFL player's underlying fantasy-producing state, inspired by the useful architectural ideas behind DARKO while remaining football-specific, interpretable, and consistent with TIBER governance.

This is a **research and architecture task only**. It does not authorize implementation, producer activation, model promotion, source admission, scheduled jobs, deployment, spending, or fantasy decisions.

## Core research question

Can TIBER maintain a persistent player-state estimate that updates as new evidence arrives and distinguishes durable role/ability changes from weekly noise better than simple rolling windows, recent-game averages, or static rest-of-season projections?

A useful conceptual decomposition to audit:

- **Role State** — snaps, routes, participation, carries, targets and role security
- **Opportunity State** — expected fantasy-producing opportunity generated by that role
- **Efficiency State** — expected production per opportunity, with appropriately slower updating where evidence is noisy
- **Team / Environment State** — offensive context and relevant Teamstate evidence
- **Uncertainty / Volatility** — how confident TIBER should be in each state estimate
- **Fantasy State** — the resulting distribution of expected fantasy production, not merely a single opaque score

Do not assume these components are correct; audit them.

## Required audit

### 1. Reconcile existing TIBER architecture

Inventory and map existing work before proposing anything new, including where relevant:

- ROP / WeeklyRoleState and existing role observations
- Teamstate / TTS
- Forecast priors and prediction machinery
- Player State Card / consumer read models
- Time-Machine / point-in-time evidence work
- current Data evidence contracts, provenance and freshness rules
- any existing Research work on stabilization, opportunity, predictive features, uncertainty or role change

Identify overlap, reusable contracts, conflicting semantics, and duplication risk.

### 2. Study the DARKO design pattern, not the basketball metric itself

Document which ideas plausibly transfer to NFL/fantasy football and which do not.

In particular, investigate:

- persistent latent/player state rather than arbitrary last-N-game windows
- sequential updating as new games arrive
- different decay / memory rates for different signals
- shrinkage toward appropriate priors
- handling injuries, depth-chart changes, team changes and role discontinuities
- uncertainty as a first-class output
- retrospective point-in-time evaluation without hindsight leakage

Explicitly identify where basketball assumptions such as possession structure and on/off impact do **not** transfer to football.

### 3. Empirical feasibility

Determine what historical evidence TIBER would need to learn rather than hand-wave:

- stabilization / persistence rates by feature
- predictive half-lives or decay functions
- priors by position, experience, archetype or other justified grouping
- treatment of low-sample rookies and newly elevated players
- relationship between role, opportunity, efficiency and fantasy points
- season boundaries and offseason information
- injury / absence effects
- opponent and team-environment effects

Recommend appropriate baselines for comparison (for example season-to-date, rolling windows, exponentially weighted estimates, existing Forecast outputs, consensus projections where admissible).

### 4. Architecture options

Compare at least three plausible approaches, including a deliberately simple baseline.

Examples worth evaluating:

1. transparent exponentially weighted / shrinkage state
2. Bayesian or state-space / Kalman-like sequential estimator
3. richer hierarchical or learned model only if the evidence supports the added complexity

For each option describe:

- inputs and evidence contracts
- state representation
- update mechanism
- uncertainty representation
- position-specific treatment
- explainability
- computational/data requirements
- failure modes
- leakage risks
- how it would integrate with ROP, Teamstate, Forecast and Fantasy without collapsing their boundaries

Do **not** optimize for producing one universal player score. Determine whether component states are more useful and defensible.

### 5. TIBER governance requirements

Any proposed architecture must preserve:

- observed evidence vs inference separation
- exact evidence provenance and freshness
- point-in-time reproducibility
- explicit uncertainty
- fail-closed behavior when evidence is unavailable or unqualified
- human/operator authority over fantasy actions
- no hidden auto-start/sit, waiver, trade or roster actions

The system should be able to explain **why its belief changed** from one checkpoint/week to another.

### 6. Evaluation design

Propose a retrospective evaluation capable of answering:

> Given only information available at time T, was the state estimate better calibrated and more predictive of subsequent fantasy opportunity/production than simpler alternatives?

Include:

- walk-forward / time-series evaluation
- leakage controls
- position-level evaluation
- calibration and probabilistic scoring where appropriate
- error metrics
- ablations for ROP, Teamstate and other components
- examples of role-change events where responsiveness matters
- examples where short-term production should *not* cause a large state change

## Requested deliverable

Return a bounded architecture/audit packet containing:

1. current TIBER capability map
2. transferable DARKO principles vs non-transferable assumptions
3. data/evidence gaps
4. candidate state schema
5. architecture comparison
6. proposed evaluation protocol
7. principal risks and failure modes
8. recommendation: **do not pursue / research further / prototype**
9. if prototype is recommended, the **smallest offline retrospective experiment** that could falsify or support the idea

Prefer falsifiable hypotheses over architecture enthusiasm.

## Boundaries

Research/read-only architecture work is authorized.

Do not:

- implement production code
- alter ROP, Teamstate, Forecast, Data or Fantasy contracts
- admit new sources
- run unapproved real-player producer pipelines
- create scheduled jobs
- deploy services
- merge changes
- spend money
- present an experimental state as a qualified fantasy ranking or recommendation

Bring any proposed implementation or empirical execution boundary back for explicit operator authorization.
