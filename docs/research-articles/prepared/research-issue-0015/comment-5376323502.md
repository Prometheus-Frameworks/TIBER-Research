### Answer first

The Context Compiler direction is compatible with the current TIBER architecture and does **not** require a wholesale rewrite.

Most of the required semantic layers already exist and are intentionally separated:

```text
TIBER-Data        → observed/source/provenance truth + canonical identity
TIBER-Teamstate   → deterministic team-environment interpretation
TIBER-Rookies     → rookie/prospect evidence and model artifacts with phase/proxy semantics
TIBER-FORGE       → deterministic fantasy-signal grading
TIBER-Forecast    → uncertain future football/fantasy outcome inference
TIBER-Strategy    → general strategy rules/ontology, not player truth
TIBER-Fantasy     → user/league context, downstream orchestration, persistence, inspection
TIBER-Ops         → authority, sequencing, operating/control plane
TIBER-Research    → replayable experiment custody and epistemic research protocol
TIBER-Harness     → provider-neutral runtime/evaluation + deterministic safety validation
```

The missing primitive is the governed **compilation boundary** between those layers and an agent:

> select only the decision-relevant state, preserve each contributing layer's identity/authority/time/uncertainty semantics, expose bounded operations, and retain a replayable trace of what was included or omitted.

The architectural risk is therefore not primarily “models need more intelligence.” It is **semantic flattening during assembly**: turning a candidate into truth, a proxy into an observation, a forecast into a fact, a stale snapshot into current state, a user thesis into Shared Reality, an unavailable value into zero, or a strategy rule into a player label.

## 3. Baseline and alternatives

### R0 — doctrine and ownership reconciliation

#### TIBER-Ops #69

Compatible. #69 already says TIBER owns governed football context and stable inspection/control while a chosen agent owns conversation/translation. Context Compiler v0 makes the missing middle explicit: TIBER must not merely store context; it must assemble a bounded, decision-specific projection whose evidence and authority survive contact with an agent.

This sharpens Phase 2 acceptance but does not reorder #69:

```text
Phase 1 audits
  → explicit lane rotation
  → smallest closed agent substrate
  → context/continuation acceptance
  → Pulse + Use TIBER packaging
```

#### TIBER-Research

Compatible as experiment owner, not automatically runtime owner. Research already has the strongest semantics for frozen inputs, source/evidence separation, attempt/review lineage, cutoff discipline, candidate-only authority, and provider-neutral agent entry. It is the right home for the R2 fixture/contract experiment and later continuation traces.

#### TIBER-Harness

Partially compatible, with one important boundary conflict. Harness already provides provider-neutral runs, deterministic validators, fixtures, schema checks, and a strong rule that model output is advisory. Those are reusable concepts.

However, the current Harness `safety_contamination` workload treats fantasy advice/recommendations as contamination because the Harness is oriented toward promotion/audit safety. A future Context Compiler continuation evaluator must **not silently reuse or weaken that workload** merely to evaluate decision-support interactions. If reusable continuation evaluation later belongs in Harness, it needs a separately authorized workload/skill boundary with its own authority and expected-output semantics.

#### TIBER-Fantasy

Fantasy is the strongest current **application-layer candidate** for eventual user-specific context assembly because it already owns league/user state, upstream adapters, canonical identity operations, context-bound entity persistence, and the thin stdio MCP pilot from merged PR #333.

That is evidence, not an ownership decision. R0 does not declare Fantasy the production compiler owner. The shared compiler contract must be designed first so application convenience does not accidentally make Fantasy the owner of upstream truth or duplicated model semantics.

#### Ops #67 / Fantasy #338

Both remain complementary rather than duplicated:

- Ops #67 asks what capabilities a brought agent requires without repository access.
- Fantasy #338 asks what existing product surfaces/calculations/consumers actually exist.
- Research #15 asks how the resulting governed state and operations should be **compiled and behaviorally evaluated**.

### R1 — context contribution matrix

#### 1. TIBER-Data — source/Shared Reality foundation

**Contributes:** canonical identity and crosswalks; governed source data; evidence/provenance; roster/depth/player-state candidates and promoted handoff artifacts; explicit source/readiness audits.

**Agent-safe projection candidate:** compact source/evidence references by canonical entity and decision scope, carrying source identity, contract/version, clocks, authority/admission state, coverage and correction lineage.

**Must not be compacted away:** canonical entity resolution status; source/contract/version/digest; event/effective/publication/availability/retrieval clocks where applicable; governed vs candidate/fixture status; missingness; rights/source limitations; correction/supersession lineage.

**Current gaps:** current 2026 roster/availability/offensive-participation coverage remains incomplete in several audited lanes. Compiler must return explicit unavailable/unknown rather than permit narrative substitution.

#### 2. TIBER-Teamstate — deterministic environment interpretation

**Contributes:** pace, pass tendency, scoring environment, stability/volatility, movement windows and other team-level interpretations from governed upstream inputs.

**Agent-safe projection candidate:** decision-scoped current/dated team-environment reference plus interpretation tags and source/governance metadata.

**Must not be compacted away:** input/source provenance; season/week/window; deterministic rule/version; governance state (`governed | fixture | ungoverned | unknown` where carried); publication-enabled state; warnings and insufficient-data state.

**Current gaps:** presence of a Teamstate artifact does not prove current 2026 publishable team reality. Publication/fixture status must survive compilation.

#### 3. TIBER-Rookies — prospect/rookie evidence and transition state

**Contributes:** Rookie Alpha, pre-draft model outputs, promoted handoffs, official draft/transition facts, historical reconstruction, Devy discovery and uncertainty scaffolds.

**Agent-safe projection candidate:** phase-aware rookie/prospect context packet reference separating frozen pre-draft baseline, official post-draft facts, current transition evidence, and discovery-only material.

**Must not be compacted away:** pre-draft vs post-draft phase; model/version/generated-at; proxy vs official/source-verified evidence; promoted vs discovery/non-promoted state; frozen baseline vs later update; missing/partial input coverage; provenance.

**Current gaps:** proxy-limited and discovery artifacts coexist with promoted outputs. Flattening them into one “rookie grade” would destroy the repository's temporal/hindsight protections.

#### 4. TIBER-FORGE — deterministic fantasy-signal grading

**Contributes:** contract-driven fantasy signal grades, tiers, component evidence and confidence over governed inputs. Current promoted player-static cohort is reproducible and player-specific at the surfaced head.

**Agent-safe projection candidate:** player signal record with grade/tier/components/confidence plus full source/input provenance and coverage state.

**Must not be compacted away:** `score_source` / evidence provenance; component evidence; confidence; input artifact identities; generated/default/fallback semantics if present; missing artifact != zero.

**Current gaps:** FORGE is still not live-ingestion-backed and should never become source truth merely because a grade exists.

#### 5. TIBER-Forecast — uncertain future outcomes

**Contributes:** xFPG, replacement/VORP, weekly/ROS scoring, ranges, confidence/stability, and governed forward-publication contracts. Forecast explicitly owns inference about uncertain future outcomes, not observed reality or advice.

**Agent-safe projection candidate:** forecast distribution/reference for a declared decision scope with model/run/version, exact cutoff/input bindings, scoring/league context, range/confidence/fragility, and typed unavailable states.

**Must not be compacted away:** `model inference` epistemic class; model/run/version; cutoff; input identities; scoring profile/league context; floor/median/ceiling or other uncertainty representation; confidence/volatility/fragility; publication/admission status; unavailable reason.

**Current gaps:** compute-service availability/auth is a transport concern and must not be confused with artifact authority. Compatibility/legacy scenario surfaces must also remain identifiable as such.

#### 6. TIBER-Strategy — decision vocabulary/rules

**Contributes:** deterministic strategy ontology, roster-state concepts, player-asset archetype rules, timeline rules and explanation templates.

**Agent-safe projection candidate:** retrieve applicable concept/rule definitions and their required evidence, not a pre-labelled player verdict.

**Must not be compacted away:** “rule vs instantiated label”; required evidence fields; unavailable/future-contract inputs; rule/version; consumer-side application boundary; human decision authority.

**Current gaps:** age, draft year/experience, role/contract security, market liquidity and other declared future inputs mean many rules cannot yet honestly instantiate. `no input, no label` must remain compiler-visible.

#### 7. TIBER-Fantasy — user/context assembly and downstream application

**Contributes:** league/roster/team context, user-facing orchestration, upstream adapters, coverage/unavailable states, canonical identity operations, persisted operator-local entity models, and the current thin MCP adapter evidence.

**Agent-safe projection candidate:** workspace/league/decision context plus references to upstream governed state, with operator-local context explicitly separated from Shared Reality.

**Must not be compacted away:** workspace/user/league scope; privacy class; canonical identity; source path/fallback used; missing/coverage state; operator-local vs Shared Reality; decision state; final action authority = human.

**Current gaps:** legacy/transitional model fallbacks still exist. A compiler cannot quietly erase which producer actually generated a value or treat a compatibility fallback as canonical ownership.

#### 8. TIBER-Ops — control plane

**Contributes:** authority state, active/parked lane sequencing, operator decisions, activation/promotion boundaries and cross-repo coordination.

**Agent-safe projection candidate:** only the minimal control metadata needed for the exact operation (authority ceiling, permitted operations, relevant active/parked state), normally separate from football evidence.

**Must not be compacted away:** exact authority class/scope when consequential; expiry/state pins where applicable; decision owner; lane/activation boundary. GitHub labels/text/account identity alone are not human authority under #66.

**Current gaps:** Ops intentionally has no runtime. The Context Compiler must not turn Ops into the application backend.

#### 9. TIBER-Research — bounded experiment/replay custody

**Contributes:** frozen inputs/cutoffs, source receipts, epistemic classes, candidate packets, attempts, reviews, seals, causal paths/Missing Witnesses, provider-neutral agent-entry protocol.

**Agent-safe projection candidate:** bounded research findings/candidates with explicit authority ceiling and locator/digest, plus operator-local thesis objects when appropriate.

**Must not be compacted away:** candidate/unpromoted status; cutoff; source receipts; observed/inferred/forecast distinction; unresolved items and RFIs; attempt/review/seal identity; operator stance and local scope.

**Current gaps:** Research intentionally cannot promote itself into Shared Reality. Contract-shaped output must remain candidate-only until the receiving lane performs its own governance act.

#### 10. TIBER-Harness — agent/model evaluation substrate

**Contributes:** provider-neutral execution, fixtures, JSON/schema validation, deterministic overrides, prompt-injection handling, advisory-model/authoritative-validator separation.

**Agent-safe projection candidate:** none as football truth. Harness is evaluation infrastructure around packets and outputs.

**Must not be compacted away:** provider/model/run identity; fixture identity; deterministic validator result; model result vs authoritative validator result; synthetic/non-production status.

**Current gaps:** current fantasy-contamination semantics are intentionally incompatible with normal fantasy decision-support outputs. Do not weaken them; create a new workload boundary if Harness later owns reusable continuation evaluation.



## 5. Interpretation and assessment

**Preserved assessment boundary:** This R0/R1 edition reports doctrine/census readiness for operator review and proposes R2; it does not include later R2 field contributions or activate provider execution.

### Cross-system invariants: fields the compiler must never flatten away

These are the shared non-compressible semantics discovered across the census:

1. **Canonical identity + resolution state** — entity ID alone is insufficient when resolution is ambiguous/unresolved/merged.
2. **Time** — season/week/as-of/cutoff/effective/publication/availability/retrieval times are not interchangeable.
3. **Source identity** — owner, contract/version, artifact/reference and content identity/digest where governed.
4. **Epistemic class** — observed/source fact, deterministic derivation, forecast/model inference, strategy rule, operator-local belief/context and agent inference remain distinct.
5. **Authority/governance state** — fixture, candidate, unpromoted, admitted/promoted, unavailable, disabled and published are different states.
6. **Missingness and coverage** — `null`, zero, unavailable, stale, contradicted, not-found and evidence-of-absence are different.
7. **Proxy/fallback/default semantics** — proxy participation is not routes; generated baseline is not player evidence; compatibility fallback is not canonical ownership.
8. **User/workspace scope** — private/operator context may affect the projection without becoming Shared Reality.
9. **Model uncertainty and run identity** — forecast/model outputs require their run/version/cutoff and uncertainty state.
10. **Action/authority boundary** — available operation, read/write class, authority ceiling and final decision owner must remain explicit.

Everything else is eligible for compaction **only if** the `ContextCompilationTraceV0` can show what was omitted/transformed and why.



### Preferred packet architecture

Do not embed a miniature copy of every repository into every prompt.

Preferred shape:

```text
request / decision scope
        ↓
compiler resolves canonical entities + user/workspace scope
        ↓
selects compact high-signal state from each required owner
        ↓
embeds decisive state + typed unknowns/conflicts
        ↓
references deeper artifacts through stable retrievable locators
        ↓
attaches bounded operation manifest
        ↓
agent continuation
```

The compact packet is the **working set**. The compilation trace is the **audit set**. Large source artifacts stay in their owning lanes and are retrieved only when the agent needs them.

## 6. Unknowns and revision triggers

### Main blockers / contradictions

#### B1 — no shared compiler contract

There is currently no cross-repository contract defining the minimum layer tags, clocks, authority, source identity, user scope, inclusion/exclusion trace and operation manifest required for an agent-facing packet. This is the primary R2 gap.

#### B2 — current-world evidence is incomplete

2026 roster/availability/route-participation and related current-state evidence remain incomplete or blocked in existing Data/Research audits. The compiler must make this incompleteness legible; it cannot solve missing upstream witnesses by compression or LLM inference.

#### B3 — production compiler ownership is unresolved

Fantasy is the strongest application candidate, but declaring it owner before the shared contract exists would risk recreating producer semantics in the product layer. Ownership should be an R2 output or later explicit Ops decision.

#### B4 — Harness workload mismatch

Harness has useful provider/evaluation mechanics, but its existing promotion-oriented fantasy-contamination rules are not the semantics of a decision-support continuation evaluator. A separate workload boundary is required before reuse.

#### B5 — fallback/proxy coexistence

Fantasy, Rookies, FORGE, Teamstate and Data all contain some combination of legacy, fixture, candidate, proxy, fallback or publication-disabled states. The compiler must carry those states explicitly instead of selecting whichever value is easiest to serialize.

#### B6 — no complete agent operation catalog yet

Ops #67 should inform the provider-neutral operation vocabulary. Do not design the final tool surface independently of that capability-parity audit.
