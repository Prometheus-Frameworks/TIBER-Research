## Research hypotheses

### G1 — workbench traces are distinct from model engineering traces

A persistent workbench should be evaluated on scope preservation, source/authority separation, shared-state risk, correction behavior, and meaningful stopping. These are not reducible to a single model benchmark or to Research #16’s implementation-trace dimensions.

### G2 — source-bound, one-time tasks are a valid pre-routine evaluation phase

A workbench can be assessed first through explicitly named, public, read-only tasks before any connector, credential, repository, local-computer, or scheduler surface is considered.

### G3 — self-reported non-action is advisory

A Bot’s assertion that it did not write, connect, or act externally is useful handoff context but not independent proof. A future evaluation must prefer externally generated event records and immutable source/artifact identities.

### G4 — correct completion requires terminal-state discrimination

A read-only packet that has completed its named inspection should be allowed to return `COMPLETE`. `AUTHORITY_REQUIRED` belongs only where the current task itself cannot proceed without a new grant.

### G5 — design-family similarity must not erase observation roots

Related design documents may form one intent family without collapsing their distinct observation roots: issue/comment text, immutable report bytes, PR merge state, and external tool events remain separately attributable.
